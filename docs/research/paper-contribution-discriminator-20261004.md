## Choose one main result, with the other components supporting it

Continue toward one homemade BGV exact-search system. The proposed main
systems result is a **specific, independently assured execution choice that
improves complete cost in a justified owner deployment**. Its most promising
scientific question is whether the cheapest evaluator ceases to be the best
complete service once admission, representation conversion, protected state,
acquisition and updates are paid.

We need one substantial contribution, not a separate novelty claim for every
component. The certificate and security argument can use established methods
and still be necessary supporting assurance for an original systems finding.
Conversely, a formal paper needs a substantive assurance result beyond a
routine composition, even if its implementation is fast. A fast implementation
of known methods is useful company work but does not establish either claim.

The provisional systems claim to test is:

> For exact owner-encrypted search, complete admission and retained-state costs
> create an operating frontier that evaluator-only selection misses; a
> separately checked execution plan exploits a useful portion of that frontier.

This is a hypothesis. Generic cost-aware selection is already known. The
eventual claim must identify the actual plan, invariant, deployment conditions
and measured consequence that a strongest compatible predecessor does not
already demonstrate. Do not replace that distinction with the word “joint.”

### Close a contract ambiguity before the cache gate

The selected source-scale HE reference ranks by **`(distance, original row
ordinal)`**, then returns that row's bound UInt64 ID. It deliberately uses
descending IDs. The old `coordinate_cache._result` instead ranks tuples
`(distance, numeric ID)`, and the earlier snapshot cache calls that helper.
These rules disagree on ties when IDs are not ordered like positions.
SB01 used IDs equal to positions, so its recorded comparison is unaffected.
The source gate checked its declared ordinal rule; this is not an HE arithmetic
failure or evidence that earlier score vectors were wrong.

For the current system, freeze the source reference's ordinal tie rule in the
reference function, certificate/client descriptor and every matched cache/
private selector. IDs are bound output labels, not implicit sort keys. Require
equal-distance rows with reversed and nonmonotonic IDs, before and after
updates, in Q76.4c/Q76.5. Preserve old APIs/results with their own contracts;
do not silently reuse a numeric-ID helper in the new matched control.

## The strongest compatible reference construction

Start with the following construction **before claiming a gap**. This is a
design specialization, not an execution of the authors' artifacts or a claim
that their papers provide an identical ready-made backend.

1. Use the known exact binary adaptation of HERS packing, SealPIR/MulPIR
   expansion and delayed relinearization. Instantiate the same homemade BGV
   graph, actual primes, owner inputs and complete output contract.
2. Give it a valid quantitative semantics and transformation validation in
   the style of ILA. The trusted owner supplies the semantic input premise;
   signatures bind bytes but do not establish a noise law.
3. For the strongest simple protected control, evaluate that complete graph
   once inside the trusted execution boundary and attest its input/output
   transcript, with application input/database binding in the style of Argos.
   Do not require an untrusted producer or redundant witness for this control.
4. For delegation, specialize vFHE's aggregate tensor check, preserving its
   real soundness assumptions. Use corrected ring/range/maintenance methods
   where the adapter requires them. Pay genuine prefix, suffix, commitments,
   challenges, complete coordinate checks, state and every link.
5. Add independent schedule/ownership validation and a conversion-aware
   assignment control in the style of FlowCert and Silph/CirC. Give it the same
   representations, legal placements, observations, budgets and horizon data.
6. Give the client an ordinary authenticated compact backup/cache and mutable
   updates. Allow acquisition to overlap an initial remote query. Give both
   policies the same information and charge actual overlap/invalidation.

Our proposed result has to survive this reference, rather than a control
missing compatible fusion, preparation, input binding or caching.

### Record what must remain secret, and until when

“No HE decryption key in the evaluator” does not eliminate all secret custody.
The actual signer key must still be protected. The current randomized control
card also specifies hidden fresh challenges; that custody/entropy premise
cannot be obtained for free from Argos's integrity-only CPU argument.

A stronger compatible **known commit-then-challenge control** should be
considered in Q76.5's adaptation analysis: copy and bind the entire canonical
claim, inputs/request and proposed frame irreversibly before sampling a fresh
trusted challenge. For that fixed degree-two error polynomial, the usual root
bound does not require the challenge to remain secret *after* commitment.
Fresh independent subsequent challenges allow the same conditional lifetime
union bound. This is a mathematical design observation, not an implemented or
reviewed protocol; it requires a real unpredictable entropy source, immutable
buffers, durable consumed attempts and the same full-coordinate/suffix checks.
A readable software PRNG state is not that entropy guarantee. Offline
Fiat–Shamir grinding is not covered by a quota on online verifier attempts.

This possible adapter changes challenge custody, not the three-round product
cost at the current illustrative target. It is ordinary public-coin checking,
not a new primitive or revived reusable-adjoint scheme. Keep the registered
exact control and existing hidden-challenge card unchanged. If such an adapter
is selected later, specify/prove/register it before implementation; otherwise
limit the numerical claim to the deterministic methods actually measured.

The certificate/placement catalog should therefore distinguish owner HE
secrets, attestation signing secrets, challenge unpredictability before binding,
optional post-binding challenge secrecy, query plaintext and cached plaintext.
Grant a compatible control the least restrictive *justified* custody contract;
do not obtain a performance advantage by burdening it with unnecessary secrecy.

## A structural observation that should prune the claim now

The current deterministic aggregate checker **recomputes the complete
expected aggregate**, then checks the claim. In
`_shared_query/shared_query_aggregate.cpp`, `aggregate_finish` executes
`query.expand()`, `query.aggregate()` and `query.finish_aggregate()` just as
prepared replay does. It also validates/transforms the claimed polynomials
and compares them before completing the same terminal conversion.

For g groups it performs six additional forward prime NTTs per group over the
three claimed components, plus common-Q parsing and full comparisons. Its
untrusted producer additionally evaluates and serializes the aggregate.
Prepared original-request-only execution does not need that producer or
claim. Under identical hardware, preparation and schedules, the exact seam
therefore eliminates neither the protected prefix nor any of the three
protected products per feature nor the protected suffix.

This is a source-level work-containment observation. It is not a measured
latency inequality, a lower bound for all verifiers, or a proof that all
delegation is useless. Streaming, different hardware and randomized/proof
adapters need their own accounting. Keep this deterministic control in Q77,
but close a claim that *this exact aggregate seam* accelerates arithmetic
merely because its witness is smaller than the full trace.

Likewise, three exact interpolation points for a degree-two tensor claim
force equality but pay three products, matching paired Karatsuba. Two RNS
limbs do not automatically provide 120-bit statistical soundness: an error
can live in just one limb/frequency. The existing
[product card](native-shared-query-product-control-card-20261004.md) retains
that argument. Three-round amplification at its proposed lifetime target is
a known control, not a novel probability or verification lower bound.

The research opportunity that remains is to establish a useful **different
complete admissible execution**, or a substantive refinement result, rather
than relabeling this recomputation as a faster check.

## Make the certificate and theorem handoff specific

### Promote one concrete execution question

The primary candidate is **outsourcing dynamic representation construction
only when its complete admission is cheaper than constructing it inside the
protected boundary**. In the full-relation plan, the untrusted producer
supplies canonical common-Q expansion sources. Public admission parses their
shared integers, derives digits, lowers both limbs and checks the complete
relation. Prepared replay derives those sources internally from the original
ciphertext. Both finish the same exact frame.

Test whether avoiding particular inverse-transform/CRT/source-construction
work outweighs the producer, approximately 120MiB witness, parsing, additional
transforms and state. This is unmeasured. Replay's common-Q CRT/digits already
use fixed-width native arithmetic; only the terminal codec uses GMP. Do not
motivate a result with Python/GMP conversions absent from this comparator.

The exact aggregate seam is a **negative control for redundant delegation**:
it recomputes expected products rather than avoiding them. Preserve and measure
its overhead, but do not start another kernel project expecting a speedup from
its witness reduction alone. Randomized/proof delegation needs its separately
justified relation and paid adapter.

`OwnerOrigin`, a valid certificate and correctly implemented deterministic

Freshness and at-most-once release require their explicitly stated authority,
storage and client rules. Availability is not guaranteed. Ordinary trusted

The confidentiality argument couples authorized private outputs to exact

separately name augmented evaluation-key/KDM assumptions, authentication/hash

permitted application/private leakage. Public arithmetic integrity is not raw

private timing, operating system or hardware.
