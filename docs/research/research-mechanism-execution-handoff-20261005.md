## What to build, and what could justify a paper

Build an exact owner-data search service around the homemade BGV arithmetic,
with authenticated enrollment, original-query binding, complete arithmetic
admission, current snapshot authority and verification before private decoding.
Retain the production Paillier path, homemade BFV, existing CUDA work and
optional imported reference artifacts. The selected protected graph is a CPU
prototype; its future GPU version must implement that same admitted graph.

The research target is **a particular representation or verification boundary
that safely removes necessary paid work**. The company system is a deliverable
even if every currently proposed mechanism is an adaptation of known methods.
An original paper requires a surviving distinction and evidence; it is not
guaranteed by completing the implementation.

## Worked closest construction: why the update template is insufficient

Grant the reference known packed search, a trusted integrity-only evaluator or
properly checked delegation, an authenticated dynamic map, owner-retained
plaintext, compact patches and ordinary immutable-base storage. For fixed
ordered IDs, define `D_e[r] = U_e[r]` when ordinal `r` is in the current map,
and `D_e[r] = B[r]` otherwise.

Both our template and the reference can execute these same steps:

1. Keep the same honest encrypted base and prepared native representation.
2. Authenticate a current recipe containing its physical identity and the
   bounded latest-replacement map; deliver replacement values confidentially
   to the owner and obtain freshness from the same trusted authority.
3. Sign one request binding the original encrypted query, nonce and recipe.
4. Run the same complete base evaluator/admission graph; issue a receipt
   binding that exact frame and the complete current recipe.
5. Authenticate and consume before private decoding. Replace changed-row
   distances with local popcounts, then select stable top3 over all rows.
6. Use the same overwrite, compaction and crash/in-flight-update law.

For the same base answer and replacement values the executions have identical
functionality and abstract work. Their support invariant is also the same:
one current value per ordinal, complete IDs and coverage, same original query,
and public authorization before private consumption. Therefore base-plus-delta,
local correction, version labels and a signed recipe **alone** cannot distinguish
a new algorithm. This is a constructive objection to that abstract template,
not a reproduced author-system latency, a lower bound, or an audited theorem
about all prior implementations.

For 32 changed 512-bit rows, the local value body is 2,048 B. The proposed encrypted
tile instead needs a 245,760-byte coefficient body, an HE product/relinearization
and a 102,400-byte extra terminal body per query. Both must pay actual delivery,
authentication and owner key provisioning. An encrypted tile is eligible only
if a *necessary additional cost* it removes under the actual owner contract
survives that comparison. Do not time a dominated tile merely to collect a row.

The prior-work obligations are concrete. [PPMI v3](https://arxiv.org/html/2506.17336v3)
already supplies dynamic encrypted search, decomposed queries and cached key
representations; an exact binary, fresh/admitted adapter must be built and paid.
[Argos](https://petsymposium.org/popets/2025/popets-2025-0099.php) supplies an
integrity-only hardware-backed FHE control. [vFHE](https://arxiv.org/html/2301.07041v2),
Appendix D, supplies randomized checks for delegated batched products; our current
deterministic aggregate checker does not implement its saving. A broader
delegation claim needs that actual maintained-graph adapter.
The fixed enrolled contraction is also a standard Slalom-style linear operator
in the genuinely expanded query. Its dense preprocessed check is an additional
strong reference, not a new algorithm. Our E70/E71 already supply the known
quotient and tiny encrypted-query controls; their preparation, feedback and
wire losses remain in the comparison. The concrete handoff separates those
control costs instead of treating all “randomized checking” as the same model.

[Additive-homomorphic functional commitments](https://eprint.iacr.org/2022/1331),
Definition 8/Appendix A.4, establish function-dependent verifier preprocessing and
updatable commitments for expressive verified database queries.
[Verification-efficient homomorphic signatures](https://eprint.iacr.org/2025/110),
Definitions 2.5/A.9, also formalize verification preprocessing and authenticated
computation on data streams. These are predecessors, not ready-made measured
common-Q BGV adapters. Retain field/ring conversion, range/rounding, honest
origin, freshness and release costs before proposing one. No new proof-backend
experiment is added by this reading.

## The eligibility return that selects the one extension

R4's first deliverable is a short mechanism specification with two literal
source-to-release graphs: the proposed execution and the strongest compatible
reference. Mark every vertex by its inputs, authorization, arithmetic and
maintenance obligations, placement and lifetime. Hashing or signing an
unchecked vertex does not certify its computation.

Separate reusable and query-dependent state. A transform of fixed enrolled
inputs may be reused while those exact inputs/code/profile remain pinned.
Fresh query expansion depends on the new encrypted query and cannot inherit
another query's admission merely because their plaintext bit patterns match.
An old physical base may remain a component, but current logical authority and
the owner's complete recipe still change. Define dependency-based invalidation
and atomic publication explicitly; ordinary dependency caching is not the
claimed contribution.

The return must supply all of the following before an expensive extension run:

| Item | Literal completion check |
| --- | --- |
| Mechanism | One actual changed segment, representation or retained-state lifetime; distinguish it from the three implemented remote modes. |
| Supporting invariant | Explain input origin, all common-Q coordinates/limbs, noise/terminal validity, currentness, coverage, private-consumption order and update/compaction behavior. |
| Incremental resource vector | Exact setup/update/encryption/preparation counts, both transfer links, transient/persistent state and extra per-query work. Unknown adapter costs stay unknown. |
| Compatible reference | Grant identical ordinary rewrites, prepared state, streaming, caching, compact updates, owner permissions and policy information. If graphs/protocols coincide, record containment. |
| Causal ablation | Disable precisely the mechanism while preserving all rows, IDs, queries, output and arrival law; use the strong reference as a separate competitor. |
| Prediction | Attribute R3's bottleneck and freeze a deployable crossover/compaction rule using calibration only. Specify a predicted losing regime. |
| Falsifier | No useful complete-cost region, missing binding, same compatible construction, or a premise contradicting owner permissions closes the proposed main claim. |

Implementation novelty does not satisfy this return. Neither an implementation
gap in the reference nor a search finding no similarly titled paper establishes
priority. A supporting reduction becomes a main contribution only if it gives
a substantive prior-separated guarantee, not as an automatic fallback for a
contained algorithm.

## Paper construction after the mechanism decision

Use one central statement: the exact execution change, its necessary invariant,
the paid work it removes, the applicable prior construction and the conditions
where it helps. Put the claim's prior-work objection next to the claim, rather
than describing every earlier experiment as a separate contribution.

The paper should contain the owner/malicious-cloud functionality and leakage;
the selected source-to-release graph; the mechanism and supporting theorem;
the strongest compatible reference and causal ablation; complete setup,
acquisition, queries, updates, traffic and live-state results; winning/losing
regimes; and the actual attestation/parameters/private-side-channel premises.
Use the portfolio's contained/failed ideas to explain design choices, not to
inflate the contribution count.

If the original result is an assurance theorem, its statement and refinement
must be substantively distinct and externally reviewed. If it is a systems
finding, it needs a generalizable mechanism and complete held-out/deployment
evidence. The target venues do not relax either obligation. No publication
readiness, fastest-system claim or completed security reduction follows from
this planning review.
