## E82 proposal: paid authenticated fixed-matrix correlations

**Proposed, not implemented.** R4/P03/P07/P10. Preserve all earlier experiment
IDs. Initial allocation: one contract/negative/count session, then one actual
primitive-interface session only if a complete plausible design survives.

The owner-generated token interface to replace is not merely random shares:

```
client gets fresh private r in the actual query field
client gets a correctly distributed fresh encryption of Scores_M(r)
client can establish its approved provenance before any response decryption
server sees only its allowed public context/packet/query leakage
```

M is the owner's **fixed private matrix**, not a random public matrix; its
concrete row blocks are F32/F23 in the legacy layouts and85/256 in the strong
global controls. Plaintext masking is in t; encryption/checking is in full Q.
Any seed construction must reconcile that field/lift distinction and preserve
fresh encryption/error law, source binding and exact output. A public fingerprint
of a server-chosen initial answer does not authenticate its encryption law.

Three competing representations must be priced before HE code:

1. **Secret low-dimensional mask code with controlled refresh.** Secret code,
   fresh/fixed coefficients, sparse/noisy correction and setup M*code are all
   explicit. Noiseless reused subspace is a mandatory negative: repeated same-
   query deltas reveal mask-span differences even when the query transform is
   private. A fresh per-query code may hide it but requires paid matrix work.
   Give zero-noise/known-query/unknown-offset controls before assuming LPN.
2. **Recipient-specific programmable correlations.** Extract the exact client/
   server/owner functionality of a concrete prior PCG/EMVP construction, then
   specify an adapter for fixed M and fresh encrypted outputs. A generic PRG,
   random matrix triple or unspecified encrypted correction is not that adapter.
   Internal security dimension can exceed the application width, but its state,
   projection/carry, setup, traffic and generation cost must be paid.
3. **Sparse/block-preserving private correction.** Permit structured correlations
   only with a proof for their distribution and every fresh error/seed. Compare
   actual row matrices and the E49 vectorized owner control; do not substitute
   a large ambient query dimension for those small blocks. Reuse/refresh and
   failed/batched preparation enter the lifetime cost.

The first deliverable is a transcript/roles card plus independent field oracle
for zero-noise span leakage and complete setup/reuse counts. Proposed paths:
`experiments/bfv_search_lab/secret_code_mask_oracle.py`, its test,
`benchmarks/secret_code_mask_lab.py`, and a research report. They do not exist yet.
Only after a survivor should the actual programmed encrypted-token adapter be
implemented; a homemade implementation remains the deliverable, external
artifacts the strongest controls.

**Required failures:** fresh mask disclosed to the server; known/unknown-query
span leakage; server-computable encryption noise or mask coefficients; low-state
client secretly retaining the full coordinate matrix; bogus initial answer
accepted by hashing that answer; independent t/Q/RNS correction; uncharged
owner/helper work; field-entropy heuristic presented as128-bit assurance.
An owner's code-refresh cost is not automatically amortizable beyond a proved
transcript-reuse budget.

**Stop rule:** reject a literal recipe if all savings become the same dense
owner correction, its mask/encryption distribution fails, or the strongest
complete cost dominates. Credit the exact closest construction; do not claim
that rejecting a noiseless code disproves noised/recursive/programmable PCGs.
Return to R6 with a complete interface and one specific new step, or a scoped
negative. No native/GPU acceleration of an unpaid interface.
