Q57 formal atomic counts are not a lower bound on native memory. Its maximal
affine representation at 8k has 1,018,622 atoms; choosing a vector for each atom
is a poor sufficient representation, while bundling by source is a different
generic control. Known compiler simplification, materialization and memory
scheduling receive the same opportunities. KeyMemRT's typed shared-key liveness
is recorded as relevant prior work; neither its compiler nor other paper
performance has been reproduced here.

For Q59, fixed diagnostic coins alter two accumulated query vectors per prime
and round (the declared uint64 model is 1.5 MiB), while non-query coefficient
maps stay unchanged. Modeled canonical Q120 encrypted-tile bodies are 491,520 bytes per
tile. A single row commonly requires replacement of its whole encrypted tile.
This does not establish constant-time/sublinear update work or actual resident
GPU invalidation. Fresh coins invalidate the selected materialized adjoints;
the fully bundled maximal-cut model charges 2,414,346,240 bytes at 8k or
6,437,732,352 bytes at 32k, plus weights, context and scratch. These are models,
not measured state or universal minima.

## Concrete construction handoff

For company engineering, the tested base is the existing homemade GPU producer
plus this isolated public native verifier. Keep a prepared full replay control;
it may be faster than a stage checker in some regimes and must be measured.
Do not replace production or the earlier exact-computation verifier on the
strength of these correctness tests. The next useful engineering component is
an owner-authenticated native tile-replacement API. It should publish immutable
snapshot/epoch identities atomically, ensure evaluator and checker state equal
a fresh enrollment, abort or retain requests on the old snapshot explicitly,
and reject every old/new block/key/query mixture. Use fresh coins initially;
charge full rebuilds rather than borrowing the public fixed-coins result.
Measure row, tile, dispersed32 and whole-snapshot scripts against equally
mutable generic and fresh rebuild controls. This API is planned, not built here.

For the research path, a new proposal must supply a specific additional
mechanism before another large benchmark: an exact change to the nonlinear
canonical-maintenance boundary, a compact sufficient checking representation
that the strongest generic control cannot derive, or a new justified security
result for a complete maintained deployment. State its equation/algorithm,
closest primary theorem or construction, complete-resource distinction and a
small falsifier. A vague shared-key, affine-delta or TEE claim will repeat this
cycle. Treat these as screening questions, not newly accepted hypotheses.

The canonical digit/terminal boundary is the concrete bottleneck exposed here:
small client answers can coexist with a large GPU-to-checker tape or substantial
trusted suffix. A worthwhile new mechanism would have to reduce that **paid
complete** cost, or deliver a new reviewed assurance result, against compatible
known techniques. Keep the existing exact nonlinear oracle and generic controls
as mandatory tests. Do not reopen E101/E110 or discard the allowed cache simply
to create a positive comparison.

A paper can currently report the engineering artifact and scoped negative
comparisons. It cannot claim a novel cryptographic construction, production
privacy, an original compiler/update mechanism, or a secure-service speedup.
CSF/FHE.org readiness requires claims supported by the actual selected
algorithm, assurance argument and complete evaluation; a venue name does not
change this evidence gate.
